# Bitlathe — Architecture

Bitlathe is a native macOS developer toolbox: 90+ offline utilities, a detection
engine that guesses what you pasted, pipelines that chain tools, user scripts,
a CLI, a menu-bar Quick Panel and Shortcuts/URL-scheme integrations. Everything
runs on-device. Nothing touches the network.

## Modules

```
bitlathe/
├── Package.swift                local Swift package (all logic)
│   ├── BitlatheCore             tool protocol, registry, detection, pipelines,
│   │                            history store (SQLite), settings, JS runtime host
│   ├── BitlatheUI               design tokens + shared SwiftUI/AppKit components
│   │                            (CodeEditor, SplitPane, OptionBar, StatusStrip…)
│   ├── BitlatheTools            one folder per tool: Engine (pure) + optional View
│   ├── BitlatheCLI (`bl`)       command-line front end reusing the same engines
│   └── BitlatheTests            unit tests for every engine + registry invariants
├── App/                         Xcode app target (generated by XcodeGen, project.yml)
│   ├── Shell                    NavigationSplitView, windows, tabs, palette
│   ├── MenuBar                  status item + floating Quick Panel (NSPanel)
│   ├── Services                 macOS Services provider
│   ├── Intents                  App Intents (Shortcuts / Spotlight)
│   └── Settings                 settings scenes
├── Integrations/                Raycast extension, Alfred workflow, Quick Look
├── Distribution/                Homebrew cask, Sparkle appcast template
├── scripts/ + Makefile          build / test / archive / notarize / dmg / release
└── Docs/                        DesignSystem, Decisions, Scripting, URLScheme, …
```

Dependency direction is strictly one way: `App → Tools → UI → Core`. The CLI
depends on `Core` and `Tools` only. `Core` has no UI imports; engines in
`Tools` never import SwiftUI (enforced by a test that greps `*Engine.swift`).

## The tool protocol

```swift
public protocol DevTool: Sendable {
    static var id: String { get }           // "json.format" — stable, used by CLI/URL/Intents
    static var name: String { get }
    static var summary: String { get }      // one line, shown in the header and palette
    static var category: ToolCategory { get }
    static var symbol: String { get }       // SF Symbol
    static var keywords: [String] { get }
    static var samples: [ToolSample] { get }        // empty-state examples
    static var io: ToolIO { get }                   // text / binary / image / file / dual input
    static var optionFields: [OptionField] { get }  // declarative options → generic UI + CLI flags
    static var sideEffects: Bool { get }            // never auto-run by detection if true
    associatedtype Options: ToolOptions            // Codable & Sendable, default init
    init()
    func run(_ input: ToolInput, options: Options) async throws -> ToolOutput
    static func detect(_ sample: String) -> DetectionScore?
}
```

* **`ToolInput` / `ToolOutput`** wrap a `ToolPayload` enum (`.text`, `.data`,
  `.image`, `.file`, `.none`). An output can carry extra *facets* (named
  secondary payloads, e.g. every case variant of a string), *metadata* rows for
  the inspector and *annotations* (ranges with a style, used for highlighting).
* **Options** are plain `Codable` structs. Each tool also publishes
  `optionFields`, a declarative description (`toggle`, `picker`, `stepper`,
  `text`, `secret`) that the generic option bar renders and the CLI turns into
  `--flags`. The UI edits an `OptionValues` dictionary and decodes it into the
  typed struct before every run, so engines never see untyped data.
* **Errors** are `ToolError` values with a message, optional `(line, column)`
  location and an optional hint. The editor underlines the location.
* **Type erasure.** `AnyTool` wraps a concrete tool in closures
  (`run(input, optionValues)`, `detect`, metadata) so the registry, palette,
  detection engine, CLI, pipelines and App Intents all work on `[AnyTool]`.

### Registry

`ToolRegistry.shared` is built once at launch from `BitlatheTools.allTools`
(a static array — adding a tool means adding its folder and one line in
`ToolCatalog.swift`; a unit test fails if a tool is missing from the catalog).
User scripts are loaded by `ScriptLoader` and registered as `AnyTool`s, so they
appear everywhere native tools do. Pipelines are registered the same way.

### Generic tool screen

Most tools need no custom view. `ToolScreen` renders: header → options bar →
input editor | output pane → status strip. The output pane picks a renderer
from the payload type (code editor, image, table, tree, key/value list).
Tools that need more (colour, regex, diff, JWT, cron builder, QR, hex viewer,
CSV, URL parser, timestamps…) provide `customView` and still get the header,
status strip and standard actions for free.

## Smart detection

`DetectionEngine.detect(_:)` trims the sample to 64 KB, runs every registered
tool's `detect` (pure, synchronous, cheap — tools are required to bail early
using length and first-character checks), drops `sideEffects` tools and the
user's ignore list, and returns results sorted by confidence. The main window
runs it on paste and (optionally) on window focus; the Quick Panel runs it on
the clipboard. The top match is opened with the input already applied; the next
matches are shown as "Also try" chips. Detection has a hard budget: the engine
records timing and a test asserts < 20 ms for the fixture corpus.

## Pipelines

A `Pipeline` is `[PipelineStep]` where a step is `(toolID, optionValues, enabled)`.
`PipelineEngine.run` feeds the output payload of each step into the next and
records every intermediate output, duration and error. Pipelines are persisted
as JSON by `PipelineStore` (also the export format), get an `AnyTool` wrapper so
they can run from the palette, CLI (`bl pipe "a | b | c"` or `bl pipeline <name>`),
URL scheme and Shortcuts.

## User scripts

JavaScript files in the scripts folder are parsed for a `/** @bitlathe {...} */`
header (name, description, icon, keywords, detect regex). Each run creates a
fresh `JSContext` with a tiny API (`input.text`, `input.selection`,
`input.fullText`, `postInfo`, `postError`) and a 2 s watchdog. See
`Docs/Scripting.md`.

## JavaScript formatters

Prettier, sql-formatter, terser, marked and mermaid are bundled as resources
and executed in `JavaScriptCore` through `JSRuntime` (an actor, one warmed
context per bundle, lazy-loaded on first use, no Node, no network).

## Concurrency model

* Swift 6 language mode with strict concurrency across all targets.
* Engines are value types; `run` is `async throws` and runs on the cooperative
  pool. Heavy engines check `Task.isCancelled` between chunks.
* `ToolSession` (`@MainActor @Observable`) owns input/options/output for one
  tool screen. Edits are debounced (120 ms) and each run is a child `Task`
  that cancels the previous one. Runs longer than 150 ms show a progress
  indicator with a cancel button.
* Stores (`HistoryStore`, `PipelineStore`, `UsageStore`) are actors over a
  single SQLite connection (system `SQLite3` module — no ORM dependency).
* Settings are a `@MainActor @Observable` class backed by `UserDefaults`.

## Code editor

`CodeEditor` is Bitlathe's own `NSViewRepresentable` around `NSTextView`
(TextKit 1, non-contiguous layout for large files) with a line-number ruler,
regex-based syntax highlighting for the ~15 languages tools emit, error
underlines, invisibles, the system find bar (⌘F / find & replace), bracket
matching, font zoom and six themes. We evaluated CodeEditSourceEditor
(Tree-sitter) and STTextView; both are good but pull in large dependency graphs
and chase the newest Xcode, and the 100+ tools mostly show *output* where
Tree-sitter's incremental parsing adds little. The whole editor is behind the
`CodeEditor` view so it can be swapped later without touching tools.

## Persistence

| Data | Where |
|------|-------|
| History, favourites, usage counts, pinned inputs, clipboard history | SQLite in `~/Library/Application Support/Bitlathe/bitlathe.sqlite` |
| Pipelines | same DB (`pipelines` table, JSON blob) + export/import files |
| Preferences, window state, per-tool layout | `UserDefaults` via `Settings` |
| User scripts | user-chosen folder (security-scoped bookmark) |

## Integrations

* **URL scheme** `bitlathe://tool/<id>?input=…&action=copy|open|replace`,
  `bitlathe://pipeline/<name>?input=…`, `bitlathe://detect?input=…`.
* **App Intents**: `RunToolIntent` (tool + text + options JSON),
  `RunPipelineIntent`, `DetectIntent`.
* **CLI** `bl`: `bl <tool.id> [--opt value] < in > out`, `bl detect`, `bl pipe`,
  `bl pipeline <name>`, `bl list`, `bl --help`, `bl <tool.id> --help`.
* **Services**: "Bitlathe: Format JSON", "Decode Base64", "Smart Transform".
* **Raycast / Alfred**: thin wrappers around `bl` and the URL scheme.
* **Quick Look**: previews for `.jwt`, `.pem`, `.crt`, `.cer`, `.json`, `.yaml`.

## Distribution

Two app targets share all sources: `Bitlathe` (Direct: Developer ID, notarised,
Sparkle, Homebrew cask) and `Bitlathe-AppStore` (no Sparkle, CLI installed by an
in-app helper that copies `bl` to a user-chosen folder). A compile flag
`DIRECT_DISTRIBUTION` gates Sparkle code. `Entitlements.swift` is the seam for a
future free/pro split: every tool has `requiredEntitlement` (always `.free` today).
