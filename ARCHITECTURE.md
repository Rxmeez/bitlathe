# Bitlathe: Architecture

Bitlathe is a native macOS developer toolbox: 88 offline utilities, a detection
engine that guesses what you pasted, a command palette, per-tool history, a CLI
(`bl`), and richer custom views for the tools that need them. Everything runs
on-device. The app makes no network requests of its own (see "Web previews and
the network entitlement").

This document describes what exists in the repository now. Items that are
planned but not built are collected under "Not built yet" at the end;
[TOOLS.md](TOOLS.md) holds the per-feature checklist.

## Modules

```
bitlathe/
├── Package.swift                local Swift package (all logic)
│   ├── BitlatheCore             tool protocol, registry, detection, pipelines,
│   │                            SQLite stores, settings, JS runtime host, script loader
│   ├── BitlatheUI               design tokens + shared SwiftUI/AppKit components
│   │                            (CodeEditor, ToolScreen, OptionBar, StatusStrip, DropZone…)
│   ├── BitlatheTools            one folder per tool: Engine (pure) + optional View
│   │   ├── Tools/               engines and tool definitions
│   │   ├── Views/               custom views (JSON tree, regex, diff, CSV, web previews)
│   │   ├── Support/             shared algorithms (hashing, base-N, ASN.1, colour math…)
│   │   └── Resources/           JS bundles (Prettier, Terser, …) and the EFF word list
│   ├── BitlatheCLI (`bl`)       command-line front end reusing the same engines
│   └── BitlatheTests            test target (currently a placeholder + fixtures)
├── App/                         Xcode app target (generated by XcodeGen from project.yml)
│   ├── BitlatheApp.swift        WindowGroup, commands, settings scene
│   ├── Shell/                   sidebar, content, command palette, inspector, menu commands
│   └── Settings/                settings window
├── scripts/                     run.sh (build and launch), shot.sh (screenshots), gen-tool-table.py
├── Makefile                     generate / build / run / test / cli / lint / format
└── Docs/                        design system, decisions, licences, screenshots
```

Dependency direction is one way: `App → Tools → UI → Core`. The CLI depends on
`Core` and `Tools` only. `Core` has no UI imports, and engines in `Tools` are
written without SwiftUI so that the CLI can run them.

External Swift dependencies are two: Yams (YAML) and TOMLKit (TOML, which wraps
the C++ library toml++). Everything else is system frameworks, bundled JS, or
code in this repository. See [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md).

## The tool protocol

```swift
public protocol DevTool: Sendable {
    static var id: String { get }           // "json.format" — stable, used by CLI/URL/Intents
    static var name: String { get }
    static var summary: String { get }      // one line, shown in the header and palette
    static var category: ToolCategory { get }
    static var symbol: String { get }       // SF Symbol
    static var keywords: [String] { get }
    static var samples: [ToolSample] { get }        // empty-state examples
    static var io: ToolIO { get }                   // text / binary / image / file / dual input
    static var optionFields: [OptionField] { get }  // declarative options → generic UI + CLI flags
    static var sideEffects: Bool { get }            // never auto-run by detection if true
    associatedtype Options: ToolOptions            // Codable & Sendable, default init
    init()
    func run(_ input: ToolInput, options: Options) async throws -> ToolOutput
    static func detect(_ sample: String) -> DetectionScore?
}
```

* **`ToolInput` / `ToolOutput`** wrap a `ToolPayload` enum (`.text`, `.data`,
  `.image`, `.file`, `.none`). An output can carry extra *facets* (named
  secondary payloads, e.g. every case variant of a string), *metadata* rows for
  the inspector and *annotations* (ranges with a style, used for highlighting).
* **Options** are plain `Codable` structs. Each tool also publishes
  `optionFields`, a declarative description (`toggle`, `picker`, `stepper`,
  `text`, `secret`) that the generic option bar renders and the CLI turns into
  `--flags`. The UI edits an `OptionValues` dictionary and decodes it into the
  typed struct before every run, so engines never see untyped data.
* **Errors** are `ToolError` values with a message, optional `(line, column)`
  location and an optional hint. The editor underlines the location.
* **Type erasure.** `AnyTool` wraps a concrete tool in closures
  (`run(input, optionValues)`, `detect`, metadata) so the registry, palette,
  detection engine, CLI, pipelines and App Intents all work on `[AnyTool]`.

### Registry

`ToolRegistry.shared` is built once at launch from `BitlatheTools.allTools`
(a static array — adding a tool means adding its folder and one line in
`ToolCatalog.swift`; a unit test fails if a tool is missing from the catalog).
User scripts are loaded by `ScriptLoader` and registered as `AnyTool`s, so they
appear everywhere native tools do. Pipelines are registered the same way.

### Generic tool screen and the custom views registry

Most tools need no custom view. `ToolScreen` renders: header, options bar,
input editor | output pane, status strip. The output pane picks a renderer from
the payload type (code editor, image, table, tree, key/value list).

Tools that need more provide a custom view through `ToolViewRegistry`
(`BitlatheUI`): a map from tool id to a builder `(ToolSession) -> AnyView`.
`ToolViews.registerAll()` in `BitlatheTools` registers them at launch. When a
builder exists, `ToolScreen` still draws the header and status strip, and
replaces the options bar and generic body with the custom view. Current custom
views:

| Tool | View |
|------|------|
| `json.format` | `JSONTreeView`: text/tree toggle, search, copy path and value |
| `regex.test` | `RegexView`: pattern bar, flags, live highlights, groups, replace, explain, cheat sheet |
| `text.diff` | `DiffView`: side by side / unified, word-level highlights, folds, change navigation |
| `csv.viewer` | `CSVTableView`: sortable, filterable table with column stats |
| `html.preview`, `markdown.preview` | `WebPreviewViews`: offline WKWebView (see below) |

Adding a custom view means writing the SwiftUI view over a `ToolSession` and
registering it in `ToolViews`. Tools do not need to know about the registry.

## Command palette

`⌘K` (and `⌘⇧P`) opens `CommandPalette` (`App/Shell`), an overlay of
`PaletteSection`s built from the live state: matching tools (fuzzy-scored by
`Fuzzy` in Core, with the matched characters emboldened), actions on the
current tool (copy output, swap, clear, toggle inspector and so on), and recent
inputs from history. Every row is a `PaletteItem` whose `perform` closure does
exactly what the row says. The first nine tool rows get `⌘1` to `⌘9`.

## History, favourites and usage

`DataStore` (`Core/Stores.swift`) is an actor over one SQLite connection (the
system `SQLite3` module, no ORM). Tables: `history`, `favourites`, `usage`,
`pipelines`, `clipboard`, `custom_groups`. After a successful run the session
records `(tool, input, options)`, capped per tool (default 200) and prunable by
age. Inputs can be pinned. The inspector's History tab groups entries into
Today / Yesterday / This week / Older and lets you reload them. Usage counts feed the
sidebar's "Frequently used" section. Settings can disable history globally or
per tool; clipboard history is an opt-in setting and is off by default. Inside
the sandbox the database lives in the app container; the CLI looks for the
container's copy first so both share one file.

## Smart detection

`DetectionEngine.detect(_:)` trims the sample to 64 KB, runs every registered
tool's `detect` (pure, synchronous, cheap — tools are required to bail early
using length and first-character checks), drops `sideEffects` tools and the
user's ignore list, and returns results sorted by confidence. The main window
runs it on paste and (optionally) on window focus; the Quick Panel runs it on
the clipboard. The top match is opened with the input already applied; the next
matches are shown as "Also try" chips. Detection is meant to be cheap: the engine
records timing and the budget is meant to stay under 20 ms for typical input.

## Pipelines

A `Pipeline` is `[PipelineStep]` where a step is `(toolID, optionValues, enabled)`.
`PipelineEngine.run` feeds the output payload of each step into the next and
records every intermediate output, duration and error. Pipelines are persisted
as JSON in the `pipelines` table of `DataStore` (the same JSON is the import/export
format) and `Pipeline.asTool` wraps one as an `AnyTool`. `Pipeline.parse` reads the
`bl pipe "a opt=v | b"` expression syntax. The visual editor lives in
`App/Pipelines/` (sidebar "Pipelines" section, live per-step previews, reorder,
import/export `.bitlathe-pipeline`); saved pipelines are registered as tools so
the palette, CLI and intents can run them. The CLI resolves pipeline steps from
an immutable tool snapshot because steps run off the main actor.

## User scripts

JavaScript files in the scripts folder are parsed for a `/** @bitlathe {...} */`
header (name, description, icon, keywords, detect regex). Each run creates a
fresh `JSContext` with a tiny API (`input.text`, `input.selection`,
`input.fullText`, `postInfo`, `postError`) and a 2 s watchdog. See
`Docs/Scripting.md`. The app installs 10 example scripts on first run, watches
the folder for changes and lists load problems in Settings › Scripts.

## JavaScript formatters

Prettier 3.10.1, sql-formatter, Terser and marked are bundled as resources and
executed in `JavaScriptCore` through `JSRuntime` (an actor, one warmed context
per bundle, lazy-loaded on first use, no Node, no network). Mermaid and
highlight.js are bundled for the web previews and run inside WebKit instead.

## Web previews and the network entitlement

`html.preview` and `markdown.preview` render in a `WKWebView`
(`Views/WebPreviewViews.swift`). Markdown is converted by marked in
JavaScriptCore, highlighted with highlight.js and drawn with Mermaid, all from
bundled files.

Inside the App Sandbox, WebKit's renderer process stays blank without
`com.apple.security.network.client`, even for `loadHTMLString` with no base URL.
The owner approved adding that entitlement (`App/Bitlathe.entitlements`,
`project.yml`; recorded in `Docs/Decisions.md`), so the previews are built
defensively:

* a `WKContentRuleList` blocks every URL except `about:`, `data:` and `blob:`;
* the navigation delegate cancels everything except in-page anchors, and a
  click on an external link is handed to the default browser explicitly;
* the web view uses `WKWebsiteDataStore.nonPersistent()`;
* the HTML preview runs with JavaScript disabled.

Previewing HTML that references a remote stylesheet, script, images and an
iframe was observed to open no sockets in the app or WebKit's WebContent and
Networking processes. No other part of the app uses the network; the CLI does
not either.

## Concurrency model

* Swift 6 language mode with strict concurrency across all targets.
* Engines are value types; `run` is `async throws` and runs on the cooperative
  pool. Heavy engines check `Task.isCancelled` between chunks.
* `ToolSession` (`@MainActor @Observable`) owns input/options/output for one
  tool screen. Edits are debounced (120 ms) and each run is a child `Task`
  that cancels the previous one. Runs longer than 150 ms show a progress
  indicator with a cancel button.
* Stores (`HistoryStore`, `PipelineStore`, `UsageStore`) are actors over a
  single SQLite connection (system `SQLite3` module — no ORM dependency).
* Settings are a `@MainActor @Observable` class backed by `UserDefaults`.

## Code editor

`CodeEditor` is Bitlathe's own `NSViewRepresentable` around `NSTextView`
(TextKit 1, non-contiguous layout for large files) with a line-number ruler,
regex-based syntax highlighting for the ~15 languages tools emit, error
underlines, invisibles, the system find bar (⌘F / find & replace), bracket
matching, font zoom and six themes. We evaluated CodeEditSourceEditor
(Tree-sitter) and STTextView; both are good but pull in large dependency graphs
and chase the newest Xcode, and the 100+ tools mostly show *output* where
Tree-sitter's incremental parsing adds little. The whole editor is behind the
`CodeEditor` view so it can be swapped later without touching tools.

**Ruler inset note.** On macOS 14 and later the scroll view reserves room for
the line-number ruler through the clip view's `contentInsets.left` rather than by
shrinking the document view. "Fully scrolled left" is therefore
`x = -contentInsets.left`, not `0`, and a wrapping text view must be sized to
`clipWidth - insets.left - insets.right`. `CodeEditor.Coordinator.clipFrameChanged`
does this; forcing the origin to 0 slides the first columns underneath the ruler.

## Persistence

| Data | Where |
|------|-------|
| History, favourites, usage counts, pinned inputs, clipboard history | SQLite file `bitlathe.sqlite` in the app's Application Support folder (in the sandbox container) |
| Pipelines | same DB (`pipelines` table, JSON blob) + export/import files |
| Preferences, window state, per-tool layout | `UserDefaults` via `Settings` |
| User scripts | user-chosen folder (security-scoped bookmark) |

## Command line

`bl <tool.id> [--option value]… [file]` runs any tool (stdin when no file is
given); `bl list [--json] [--category c]`, `bl detect`, `bl <tool.id> --help`
and `bl --version` complete the surface. Option flags are generated from each
tool's `optionFields`. `bl pipe` / `bl pipeline` exist in the code but currently
trap at runtime (see "Pipelines").

## Build and distribution

Two flavours come from the build configuration (`project.yml` `BL_*` settings): Release builds **Bitlathe**
(`com.bitlathe.app`, `bitlathe://`) and Debug builds **Bitlathe Dev** (`com.bitlathe.app.dev`, `bitlathe-dev://`,
amber `AppIcon-Dev`, Shift added to the default hotkeys, a hammer in the menu bar). `AppFlavour.isDev` reads the bundle
id at runtime and `DeepLink.appScheme` reads the registered scheme, so the two run side by side with separate
containers. `scripts/install.sh` (`make install`) installs the Release flavour into `/Applications`; `scripts/run.sh`
and `scripts/shot.sh` only ever start or stop the dev app.

`project.yml` (XcodeGen) defines the `Bitlathe` app target over the local
package; `scripts/run.sh` regenerates the project, builds with `xcodebuild` and
launches (it takes one of three shared build slots so parallel workers do not
exhaust memory). The app is sandboxed with hardened runtime and
`CODE_SIGN_IDENTITY "-"` for local builds. `scripts/shot.sh` launches a tool
with a sample (launch arguments such as `-BLTool`, `-BLSample`, `-BLPalette`)
and captures the window; the launch-argument hooks live in `AppModel`.

Two app targets share one template: `Bitlathe` (Direct: Sparkle updates, `bl`
embedded in `Contents/Helpers`, `DIRECT_DISTRIBUTION`) and `Bitlathe-AppStore`
(no Sparkle, no helper). The `BitlatheQuickLook` extension is embedded in both.
`scripts/` holds archive, export, notarize, dmg and release steps; see
`Docs/Release.md`.

## System integrations

All live in `App/`: `MenuBar/` (status item, Quick Panel, Carbon global
hotkeys), `Integrations/` (`bitlathe://` deep links parsed by
`Core/DeepLink.swift`, the Services provider, headless runner, CLI installer),
`Intents/` (App Intents and App Shortcuts), `Scratchpad/`, `Clipboard/`
(opt-in developer clipboard history; the keep/skip filter is
`Core/ClipboardFilter.swift`) and `Onboarding/`. `Integrations/raycast` and
`Integrations/alfred` at the repo root wrap the `bl` CLI. Each has a document
under `Docs/`.

`Entitlement` (`Core/ToolModel.swift`) is the seam for a future free/pro split;
every tool reports `.free` today.
